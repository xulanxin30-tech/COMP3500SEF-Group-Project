## 2. Objectives

1. Provide a fixed, reproducible data baseline for integration testing across the
   React frontend, Python HTTP backend and SQLite v1.2 database.
2. Make the three business roles — **customer / merchant / driver** — concrete and
   usable: each has real, login-capable accounts and role-specific cases.
3. Cover the full implemented workflow: login → view catalogue → create waybill
   (atomic stock deduction) → status flow → tracking events → persistence.
4. Cover negative and boundary conditions at the exact points where the API and
   schema enforce them, so a regression is visible as a specific status code.
5. Provide bidirectional traceability (requirements ↔ data ↔ cases) and an
   evidence template, as required for test preparation and later reporting.

## 3. Scope

### 3.1 In scope

- `POST /api/auth/login`, `GET /api/auth/profile`
- `GET /api/health`, `GET /api/items`, `GET /api/shipments`
- `POST /api/shipments`, `PATCH /api/shipments/{id}/status`,
  `POST /api/shipments/{id}/events`
- All six schema tables, the price-snapshot trigger and
  `v_shipment_order_summary`
- Error responses 400 / 401 / 404 / 409 / 413 / 415
- Unicode (Chinese) receiver data, stock boundaries 0 and 1, duplicate-line
  constraint, price snapshot, append-only event history

### 3.2 Out of scope (blocked in the current build)

Per `docs/ui/docs/test/test-cases.md`, the following are **not implemented** and
must not become acceptance criteria for this build: user registration, address
book, service types, shipping fees, expanded logistics stages, stock-in/out
registration, dispatch/task assignment UI, delivery signature or photo proof,
timeline UI and event read API, and admin dashboard reports. Cases in file 06
therefore assert only currently implemented behaviour.

## 6. Assumptions and constraints · 假设与约束

These are the most important preparation decisions. They come from reading the
code, not from the assumed business model.

| ID | Assumption / constraint | Evidence | Consequence for the dataset |
| :--- | :--- | :--- | :--- |
| A-01 | `users.role` accepts only `customer`, `courier`, `warehouse_admin`, `admin` | B-01 CHECK | No `merchant` / `driver` role values are inserted |
| A-02 | There is no `merchant_id` or `driver_id` on `shipments`; only `sender_id` → `users` | B-01 | Merchant = a `users` row used as `sender_id`; driver is represented through `tracking_events` |
| A-03 | `_require_auth` validates the token only; it does **not** check `role` | B-03 | Every logged-in test account can call every write endpoint; a role-permission matrix is documented as a gap, not asserted as a feature |
| A-04 | Status transition order is **not** enforced; only the enum is validated | B-05, B-03 | Do not assert that `delivered → pending` is rejected |
| A-05 | Seed accounts use placeholder hashes (`hash_pwd_00x`) and cannot log in | B-01, B-02 | Dataset accounts use real PBKDF2 hashes generated by `generate_dataset.py` |
| A-06 | Tokens are process-local and expire when the backend restarts | B-02, B-03 | Re-login after every restart; do not persist tokens as test data |
| A-07 | `_read_json` requires the field set to be **exactly** equal; extra keys are rejected | B-03 | Negative cases include both missing and extra fields |
| A-08 | `Content-Type` must be exactly `application/json`; body limit 65536 bytes | B-02, B-03 | Cases for 415 and 413 |
| A-09 | `UNIQUE (shipment_id, item_id)` prevents booking one SKU twice per order | B-01 | Every `shipment_items` row uses a distinct `(shipment_id, item_id)` pair |
| A-10 | `shipment_items.unit_price` is a price snapshot; a trigger fills it when NULL | B-01 | One row deliberately keeps a historical price (145.00) below the catalogue price (150.00) |
| A-11 | `allocate_tracking_number()` generates `HK<UTCdate><seq>` | B-03 | Dataset tracking numbers use an `IT-` prefix so they can never collide |
| A-12 | Integration rows must not disturb schema seed rows or the demo account | B-06 | Explicit IDs in 101–199 only; load script deletes only that band |
| A-13 | Registration / dispatch / signature features are future scope | B-05 | No test data or acceptance expectations are invented for them |

## 7. Role mapping · 角色映射

| 中文 business role | English | schema `users.role` | Data representation |
| :--- | :--- | :--- | :--- |
| 购买物流服务的用户 | Customer / end buyer | `customer` | `users` 101, 102, 107; `shipments.receiver_name / receiver_phone / delivery_address`; US-1 |
| 使用物流服务的商家 | Merchant / shipper | `warehouse_admin` | `users` 103, 104; `shipments.sender_id`; `items.stock_quantity`; US-2, US-4 |
| 运送货物的司机 | Driver / courier | `courier` | `users` 105, 106; `tracking_events.hub_id` + `description`; US-3, US-5 |

**Mapping rationale.** The current schema has no merchant role; the only role
that owns stock and inbound registration is `warehouse_admin` (US-2), so the
merchant/shipper side of an order is exercised through that account while the
order still points at a real `sender_id`. The driver maps naturally to `courier`.
Both choices are **test-only mappings**, not a claim that the product model is
complete. If independent `merchant` / `driver` roles and a `driver_id` foreign key
are required later, that is a schema + API change needing its own task, PR and
migration — it must not be simulated by inserting values the CHECK rejects.

## 8. Test data design method · 数据设计方法

| Technique | Applied to | Resulting data / cases |
| :--- | :--- | :--- |
| Equivalence partitioning | Roles, statuses, response codes | 3 role classes × 3 status classes; positive and negative login classes |
| Boundary value analysis | `stock_quantity`, `quantity`, `unit_price` | stock 0 (`IT-ZS-105`), stock 1 (`IT-LS-104`), quantity 1 vs 2, price 0 allowed |
| State transition coverage | Shipment lifecycle | `pending` (101/104/105) → `shipped` (102) → `delivered` (103); event history 1/2/3 rows |
| Error guessing | `_read_json`, auth, FK lookups | 400 (missing/extra/invalid), 401, 404 (sender/item/hub/shipment), 409, 413, 415 |
| Constraint-based data | CHECK / UNIQUE / FK | distinct `(shipment_id, item_id)`, valid `hub_id`, non-negative stock, positive quantity |
| Data integrity / snapshot | Price trigger, summary view | historical 145.00 line; `v_shipment_order_summary` amount assertions |
| Character-set coverage | UTF-8 round trip | Chinese receiver name/address and Chinese item name (`ensure_ascii=False`) |

### Coverage summary

| Dimension | Covered values |
| :--- | :--- |
| Roles | `customer` (3), `warehouse_admin` (2), `courier` (2), plus startup `admin` (`demo`) |
| Shipment statuses | `pending` (3), `shipped` (1), `delivered` (1) |
| Hub reference | `NULL` (4 orders), hub 101, hub 103 |
| Stock | 0, 1, 10, 45, 120, 300 |
| Order lines | single SKU, two different SKUs, historical price |
| Error codes | 400, 401, 404, 409, 413, 415 and 500-not-asserted |

## 10. Data security and privacy

- All personal data is fictional; `+852-9010xxxx` numbers and test addresses are
  invented. No real customer, merchant or driver data is used.
- The password `It@2026Test` and its deterministic salts are **test-only**. The
  hash format is real so accounts actually authenticate, but the salt derivation
  is deliberately reproducible and is **not production-safe**.
- No access tokens, secrets, backups or `.db` files are committed. Tokens are
  obtained at runtime and discarded at process exit.
- AI assistance is disclosed in §1, consistent with the PR template's
  "External sources / permitted AI assistance and verification" field.

## 11. Entry and exit criteria (summary)

**Entry** — before an integration run may start: this document is reviewed; the
disposable database is created and verified (row counts 7/3/6/5/6/8,
`PRAGMA integrity_check` = `ok`); backend and frontend start cleanly; CI is
green; the tested commit SHA is recorded.

**Exit** — before the run may be called complete: all applicable cases in files
06 and 07 have an Actual Result and Status; every failure has a linked Issue;
stock and row counts are re-checked; the database is reset; evidence (commit,
browser, tester, date) is attached per the file 09 template. Full checklists are
in [09-数据准备与验收清单.md](09-数据准备与验收清单.md).
