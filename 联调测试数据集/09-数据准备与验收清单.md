# 09 · Data Preparation and Acceptance Checklist · 数据准备与验收清单

> This is the operational part of test preparation: how to build, verify, use,
> record and reset the dataset. Follow it in order. Status: **prepared, not
> executed**. All commands run from the **repository root** (the folder that
> contains `README.md` and `联调测试数据集/`).

## 1. Environment · 环境

| Item | Requirement | Check |
| :--- | :--- | :--- |
| Python | 3.12 (`py -3` on Windows, `python3` on macOS/Linux) | `py -3 --version` |
| Node.js | >= 22.12 | `node --version` |
| SQLite CLI | `sqlite3` available | `sqlite3 --version` |
| Ports | 8000 and 3000 free | no other listener |
| Database | **Disposable** file via `LMS_DB_PATH` | never `backend/lms.db` on a shared machine |
| Branch | `联调测试` | `git status` |
| Tested commit | record the SHA | `git rev-parse HEAD` |

Never run the load script against a shared, demo or production database
(`database/README.md`, `docs/ui/docs/test/test-cases.md`).

## 2. Build the baseline · 数据准备步骤

**Step 1 — point at a disposable database**

```powershell
# Windows PowerShell
$env:LMS_DB_PATH = "$PWD\backend\it_lms.db"
```

```sh
# macOS / Linux
export LMS_DB_PATH="$PWD/backend/it_lms.db"
```

**Step 2 — let the backend create the schema and the `demo` account once**

```powershell
py -3 backend/server.py          # Windows
```

```sh
python3 backend/server.py        # macOS / Linux
```

Confirm `GET http://localhost:8000/api/health` returns
`{"status":"ok","service":"lms-backend"}`, then stop the server with Ctrl+C.
This order matters: the startup routine only initialises an empty database and
adds `demo` when the account is missing.

**Step 3 — load the dataset (idempotent)**

```sh
sqlite3 "$LMS_DB_PATH" ".read '联调测试数据集/04-联调基础数据.sql'"
```

The script deletes only rows with IDs in 101–199 and re-inserts them inside one
`BEGIN IMMEDIATE` … `COMMIT` transaction. Re-running it restores the exact
baseline. It never touches schema seed rows 1–3 or `demo`.

**Step 4 — optional: regenerate the machine-readable artefacts**

```sh
python 联调测试数据集/generate_dataset.py
```

This rewrites `04-联调基础数据.sql` and `05-联调基础数据.json` from one source of
truth. Commit both outputs together if the data changes; never hand-edit them.

**Step 5 — restart the backend (and the frontend for UI cases)**

```sh
python3 backend/server.py
# second terminal
cd frontend && npm ci && npm run dev
```

Sign in with `demo / demo123` for the control case, or with a dataset account
using `It@2026Test`.

## 3. Post-load verification · 加载后校验

Run against the disposable database before any case is executed:

```sql
SELECT 'users', COUNT(*) FROM users WHERE user_id BETWEEN 101 AND 199
UNION ALL SELECT 'hubs', COUNT(*) FROM hubs WHERE hub_id BETWEEN 101 AND 199
UNION ALL SELECT 'items', COUNT(*) FROM items WHERE item_id BETWEEN 101 AND 199
UNION ALL SELECT 'shipments', COUNT(*) FROM shipments WHERE shipment_id BETWEEN 101 AND 199
UNION ALL SELECT 'shipment_items', COUNT(*) FROM shipment_items WHERE shipment_item_id BETWEEN 101 AND 199
UNION ALL SELECT 'tracking_events', COUNT(*) FROM tracking_events WHERE event_id BETWEEN 101 AND 199;
```

Expected: **7 / 3 / 6 / 5 / 6 / 8** (35 rows total).

```sql
PRAGMA integrity_check;        -- expect "ok"
PRAGMA foreign_key_check;      -- expect no rows
PRAGMA user_version;           -- expect 2
SELECT sku, stock_quantity FROM items WHERE item_id BETWEEN 101 AND 199 ORDER BY item_id;
-- expect 120, 45, 300, 1, 0, 10
SELECT COUNT(*) FROM users WHERE username = 'demo';   -- expect 1
SELECT tracking_number, status FROM shipments WHERE shipment_id BETWEEN 101 AND 199 ORDER BY shipment_id;
-- expect IT-2026-0001..0005 with pending, shipped, delivered, pending, pending
```

Optional repository-level check (stop the backend first):

```sh
python database/db_manager.py verify --db "$LMS_DB_PATH"
python database/db_manager.py status --db "$LMS_DB_PATH"
```

## 4. Execution and evidence record · 执行与证据

Run cases in the order given in [06-接口联调用例.md](06-接口联调用例.md), then
the probes in [07-异常与边界数据.md](07-异常与边界数据.md). Re-verify §3 after the
negative set. Use this template (from `docs/ui/docs/test/test-cases.md`) for
each case — one row per execution:

| Field | What to record |
| :--- | :--- |
| Test Case ID | `IT-TC-xxx` / `NEG-xxx` / `BD-xx` |
| Module / 中文 role | Feature and role under test |
| Priority | P0 / P1 / P2 |
| Preconditions | Data IDs, token, stock values, no other writer |
| Steps | Actual commands / requests issued |
| Input Data | Exact JSON body or SQL |
| Expected Result | From file 06 / 07 |
| **Actual Result** | Observed status code, body and DB values |
| **Status** | Pass / Fail / Blocked / Not Run |
| **Execution Evidence** | Commit SHA, browser + version, tester, date + time zone, request/response or screenshot |

Also record: the CI run result, the disposable DB path, and any Issue linked to a
failure. Automated backend/frontend test results must **not** be used to mark
manual browser cases as passed.

## 5. Reset and cleanup · 重置与清理

| Situation | Action |
| :--- | :--- |
| Re-run the same suite | Re-run `.read '联调测试数据集/04-联调基础数据.sql'` — it deletes and re-inserts the 101–199 band |
| Positive cases already deducted stock | Reload the script before a second run; `IT-WM-101` returns to 120 |
| End of the session | Stop the backend, then delete the disposable file (`backend/it_lms.db`) |
| Data-level negative probes | Always `ROLLBACK` the scratch transaction |
| Tokens | Discard; re-login after every backend restart |
| Never commit | `*.db`, `database/backups/`, tokens, screenshots containing personal data |

To remove only the integration rows without deleting the file:

```sql
BEGIN IMMEDIATE;
DELETE FROM tracking_events WHERE event_id BETWEEN 101 AND 199;
DELETE FROM shipment_items WHERE shipment_item_id BETWEEN 101 AND 199;
DELETE FROM shipments WHERE shipment_id BETWEEN 101 AND 199;
DELETE FROM items WHERE item_id BETWEEN 101 AND 199;
DELETE FROM hubs WHERE hub_id BETWEEN 101 AND 199;
DELETE FROM users WHERE user_id BETWEEN 101 AND 199;
COMMIT;
```

Child-first order is required because the backend enables
`PRAGMA foreign_keys = ON`.

## 6. Entry criteria · 准入准则

Complete **all** items before starting an integration run:

- [ ] This dataset specification has been reviewed by QA and at least one other team member (`CONTRIBUTING.md`).
- [ ] The tested commit SHA, browser/version, tester and date are recorded.
- [ ] A **disposable** database is selected with `LMS_DB_PATH`; a backup exists if any non-disposable DB is involved.
- [ ] Backend (`/api/health`) and frontend start cleanly; ports 8000/3000 are free.
- [ ] §3 verification passes: counts 7/3/6/5/6/8, `integrity_check = ok`, `user_version = 2`, `demo` count = 1.
- [ ] CI (`.github/workflows/ci.yml`) is green for the tested commit.
- [ ] All three role accounts can log in (`it_customer_amy`, `it_merchant_ken`, `it_driver_dan`).
- [ ] No other tester is writing to the same database.
- [ ] Out-of-scope features (§3.2 of file 01) are confirmed as **not** acceptance criteria.

## 7. Exit criteria · 准出准则

Complete **all** items before declaring the run finished:

- [ ] Every applicable `IT-TC` case in file 06 has an Actual Result and Status.
- [ ] Every applicable negative/boundary probe in file 07 has an Actual Result.
- [ ] §3 row counts and stock baselines are re-checked after the negative set; any mutation is logged as a defect.
- [ ] Every Fail / Blocked has a linked Issue with owner and expected effect.
- [ ] Traceability matrix (file 08) execution columns are filled and the summary counts match.
- [ ] Persistence case IT-TC-017 has been executed with a real backend restart.
- [ ] Evidence includes commit SHA, browser, tester, date/time zone and request/response or screenshots.
- [ ] The disposable database has been reset or deleted; no `.db`, token or personal data is committed.
- [ ] Results and limitations are reported in the linked task/PR; manual TC-001…005 are **not** marked passed by these results.

## 8. Risks and reminders during execution

| Reminder | Source |
| :--- | :--- |
| Stock assumptions break if another tester writes concurrently | `docs/ui/docs/test/test-cases.md` |

| Any logged-in role can mutate data — do not assert role isolation | `backend/server.py`, assumption A-03 |
| `merchant` / `driver` role values are rejected by the schema CHECK | DB-NEG-04/05 |
| Events are read via SQL only; no timeline UI or event read API exists | `docs/ui/docs/test/test-cases.md` |
| Chinese paths need quoting in shell/SQLite commands | This file §2 Step 3 |
| All dates in `docs/PROJECT.md` are provisional; do not treat them as course deadlines | `docs/PROJECT.md` |
