# 02 · Data Dictionary · 数据字典

> Source of truth: `database/schema.sql` v1.2. Every field below is copied from
> that schema; the "Integration range" column states what this dataset actually
> uses. API payload field names come from `docs/openapi.yaml` 0.3.0.

## 1. Enumerations and constants

| Name | Allowed values | Enforced by |
| :--- | :--- | :--- |
| `users.role` | `customer`, `courier`, `warehouse_admin`, `admin` | `CHECK (role IN (...))` |
| `shipments.status` | `pending`, `shipped`, `delivered` | `CHECK (status IN (...))`; default `pending` |
| `tracking_events.status` | `pending`, `shipped`, `delivered` | `CHECK (status IN (...))` |
| `shipments.status` (API) | same three values | `POST /events`, `PATCH /status` in `backend/server.py` |
| `shipments.tracking_number` (generated) | `HK<YYYYMMDD><4-digit seq>` | `allocate_tracking_number()` |
| Password hash | `pbkdf2_sha256$600000$<32-hex salt>$<64-hex digest>` | `hash_password()` / `verify_password()` |
| JSON body limit | 65536 bytes | `MAX_BODY_BYTES` |
| ID ceiling | 2^63 − 1 | `positive_integer()` |

## 2. `users` — accounts for all three roles

| Field | Type / constraint | Meaning | Integration range / example |
| :--- | :--- | :--- | :--- |
| `user_id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Account id; becomes `sender_id`; returned as `user.id` | 101–107, explicitly assigned |
| `username` | `TEXT NOT NULL UNIQUE` | Login name | `it_customer_amy` … `it_customer_edge` |
| `password_hash` | `TEXT NOT NULL` | PBKDF2-SHA256 hash; **placeholder seed hashes cannot log in** | Real hash from `generate_dataset.py` |
| `role` | `TEXT NOT NULL DEFAULT 'customer'` + role CHECK | Authorisation label (not enforced by API) | `customer` ×3, `warehouse_admin` ×2, `courier` ×2 |
| `phone` | `TEXT NOT NULL` | Contact number | Fictional `+852-90100xxx` |
| `created_at` | `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | Creation time (UTC) | Left to default |

API view (`User`): `{id, username, role}` only — `phone` and `password_hash` are
never returned by `GET /api/auth/profile` or `POST /api/auth/login`.

## 3. `hubs` — sorting / distribution points

| Field | Type / constraint | Meaning | Integration range / example |
| :--- | :--- | :--- | :--- |
| `hub_id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Hub id; FK target of `current_hub_id` and `hub_id` | 101, 102, 103 |
| `hub_name` | `TEXT NOT NULL` | Display name | `IT Kowloon Test Hub` |
| `district` | `TEXT NOT NULL` | Region | `Kowloon`, `Hong Kong Island`, `New Territories` |
| `address` | `TEXT NOT NULL` | Street address | Fictional test addresses |

`POST /api/shipments/{id}/events` validates a non-null `hub_id` against this
table and returns 404 when it is absent (case IT-TC-011).

## 4. `items` — sellable catalogue / inventory

| Field | Type / constraint | Meaning | Integration range / example |
| :--- | :--- | :--- | :--- |
| `item_id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Catalogue id | 101–106 |
| `item_name` | `TEXT NOT NULL` | Display name; may contain Unicode | `整合測試商品 / Unicode Item` |
| `sku` | `TEXT NOT NULL UNIQUE` | Exact-match key for `POST /api/shipments` | `IT-WM-101` … `IT-UN-106` |
| `stock_quantity` | `INTEGER NOT NULL DEFAULT 0` + `CHECK (>= 0)` | Available stock; decremented atomically | 0, 1, 10, 45, 120, 300 |
| `unit_price` | `REAL NOT NULL DEFAULT 0.00` + `CHECK (>= 0)` | Current catalogue price | 10.00, 65.00, 88.50, 99.00, 150.00, 480.00 |

API view (`Item`): `{id, item_name, sku, stock_quantity, unit_price}` with
`unit_price` cast to `float`. Boundary rows: `IT-LS-104` (stock 1) and
`IT-ZS-105` (stock 0) drive the 409 cases.

## 5. `shipments` — orders / waybills

| Field | Type / constraint | Meaning | Integration range / example |
| :--- | :--- | :--- | :--- |
| `shipment_id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Order id used in `/{id}/status` and `/{id}/events` | 101–105 |
| `tracking_number` | `TEXT NOT NULL UNIQUE` | Human-facing number | `IT-2026-0001` … `0005` |
| `sender_id` | `INTEGER NOT NULL`, FK → `users.user_id` | Merchant/shipper account | 103 or 104 |
| `receiver_name` | `TEXT NOT NULL` | Customer name; Unicode allowed | `Amy Chan`, `陳大文 / Unicode Receiver` |
| `receiver_phone` | `TEXT NOT NULL` | Customer phone | `+852-9010100x` |
| `delivery_address` | `TEXT NOT NULL` | Destination | Chinese/English test addresses |
| `status` | `TEXT NOT NULL DEFAULT 'pending'` + status CHECK | Lifecycle state | `pending` ×3, `shipped` ×1, `delivered` ×1 |
| `current_hub_id` | `INTEGER`, FK → `hubs.hub_id`, nullable | Current hub; `NULL` for API-created orders | `NULL`, 101, 103 |
| `created_at` | `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | Created (UTC `YYYY-MM-DD HH:mm:ss`) | Fixed test timestamps |
| `updated_at` | `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | Refreshed on `PATCH /status` | Fixed test timestamps |

API view (`Shipment`) adds `sender` (joined `users.username`) and an `items`
array. Orders and waybills in the frontend are two views of this same table.
`POST /api/shipments` always inserts `status = 'pending'`, `current_hub_id = NULL`
and one `shipment_items` row plus one `pending` tracking event.

## 6. `shipment_items` — order lines

| Field | Type / constraint | Meaning | Integration range / example |
| :--- | :--- | :--- | :--- |
| `shipment_item_id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Line id | 101–106 |
| `shipment_id` | `INTEGER NOT NULL`, FK → `shipments` `ON DELETE CASCADE` | Parent order | 101–105 |
| `item_id` | `INTEGER NOT NULL`, FK → `items` | Booked product | 101–106 |
| `quantity` | `INTEGER NOT NULL DEFAULT 1` + `CHECK (> 0)` | Units deducted | 1, 2, 3 |
| `unit_price` | `REAL` + `CHECK (IS NULL OR >= 0)` | **Price snapshot at order time** | 145.00 (historical), 150.00, 480.00, 65.00, 88.50, 99.00 |
| — | `UNIQUE (shipment_id, item_id)` | One line per SKU per order | All 6 rows have distinct pairs |

Trigger `trg_shipment_items_price` fills `unit_price` from `items.unit_price`
**only when the inserted value is NULL**. Row 104 keeps 145.00 while the
catalogue price is 150.00, so the snapshot behaviour can be asserted. The API
inserts the line without a price, so trigger-populated lines are also exercised
by the create-order cases.

## 7. `tracking_events` — append-only timeline

| Field | Type / constraint | Meaning | Integration range / example |
| :--- | :--- | :--- | :--- |
| `event_id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Event id; tie-break for equal `event_time` | 101–108 |
| `shipment_id` | `INTEGER NOT NULL`, FK → `shipments` `ON DELETE CASCADE` | Parent order | 101–105 |
| `hub_id` | `INTEGER`, FK → `hubs`, nullable | `NULL` for API-generated status changes | `NULL`, 101, 103 |
| `status` | `TEXT NOT NULL` + status CHECK | Status recorded at this point | `pending`, `shipped`, `delivered` |
| `description` | `TEXT NOT NULL` | Human-readable note | English, ASCII-only test text |
| `event_time` | `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | Event time (UTC) | Fixed `2026-11-19 01:xx:xx` |

API view (`TrackingEvent`) returns `{id, shipment_id, hub_id, status,
description, event_time}`. `POST /events` is **append-only** and does not change
`shipments.status`; `PATCH /status` updates the status **and** appends an event
with `hub_id = NULL`. Events are read through a read-only SQL query because no
event read API exists yet (`docs/ui/docs/test/test-cases.md` TC-003).

## 8. View `v_shipment_order_summary`

| Column | Definition | Used in this dataset |
| :--- | :--- | :--- |
| `shipment_id`, `tracking_number`, `status`, `receiver_name`, `created_at` | Passed through from `shipments` | Order identification |
| `line_count` | `COUNT(si.shipment_item_id)` | 1 for order 101, 2 for order 102 |
| `total_quantity` | `IFNULL(SUM(si.quantity), 0)` | 2 / 4 / 1 / 1 / 1 |
| `total_amount` | `IFNULL(SUM(si.quantity * si.unit_price), 0.0)` | Order 102 = 480.00 + 3×65.00 = **675.00**; order 103 = **145.00** |

Expected `total_amount` values are asserted in IT-TC-016, which is why the
historical price line exists.

## 9. Relationships · 关系

```
users (1) ──< shipments.sender_id
hubs  (1) ──< shipments.current_hub_id        (nullable)
hubs  (1) ──< tracking_events.hub_id          (nullable)
shipments (1) ──< shipment_items.shipment_id  (ON DELETE CASCADE)
items     (1) ──< shipment_items.item_id
shipments (1) ──< tracking_events.shipment_id (ON DELETE CASCADE)
```

Deletion order in `04-联调基础数据.sql` follows the arrows in reverse:
`tracking_events` → `shipment_items` → `shipments` → `items` → `hubs` → `users`.
This matters because `backend/server.py` enables `PRAGMA foreign_keys = ON`.

## 10. Fields deliberately not present

`driver_id`, `merchant_id`, `vehicle_id`, signature / photo proof, ETA, service
type, shipping fee, address book, registration fields and expanded logistics
stages do **not** exist in schema v1.2. No dataset field may be invented for
them; see assumption A-02 and risk R-01 in
[01-数据集规格说明.md](01-数据集规格说明.md).
