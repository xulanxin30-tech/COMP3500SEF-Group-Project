# 07 · Negative and Boundary Data · 异常与边界数据

> Companion to [06-接口联调用例.md](06-接口联调用例.md). All inputs below are
> **test-only** and must be executed against a disposable database. Expected
> messages are copied from `backend/server.py` and `docs/openapi.yaml` 0.3.0.
> Status: **prepared, not executed**.

## 1. Why negative data is part of test preparation

A positive-only dataset cannot detect a regression in the guards. This file fixes
the exact invalid inputs, the exact expected status codes and the exact state
that must remain unchanged, so a failure is unambiguous. Each row is linked to a
case ID in file 06 and to a requirement in [08-可追溯性矩阵.md](08-可追溯性矩阵.md).

## 4. Data-level negative cases (SQL, not HTTP)

These validate schema v1.2 guards that the API cannot reach. Run in a scratch
transaction against the disposable DB and **always ROLLBACK**.

| ID | Statement (abbreviated) | Expected error |
| :--- | :--- | :--- |
| DB-NEG-01 | `INSERT INTO items (... stock_quantity -1 ...)` | `CHECK constraint failed: stock_quantity >= 0` |
| DB-NEG-02 | `INSERT INTO shipment_items (... quantity 0 ...)` | `CHECK constraint failed: quantity > 0` |
| DB-NEG-03 | `INSERT INTO shipment_items (shipment_id,item_id) VALUES (102,102,1)` | `UNIQUE constraint failed: shipment_items.shipment_id, shipment_items.item_id` |
| DB-NEG-04 | `INSERT INTO users (... role 'merchant' ...)` | `CHECK constraint failed: role IN (...)` — proof that no merchant role may be inserted |
| DB-NEG-05 | `INSERT INTO users (... role 'driver' ...)` | same CHECK violation — proof for assumption A-01 |
| DB-NEG-06 | `INSERT INTO shipments (... status 'in_transit' ...)` | `CHECK constraint failed: status IN (...)` |
| DB-NEG-07 | `INSERT INTO shipments (... sender_id 99999 ...)` with `PRAGMA foreign_keys=ON` | `FOREIGN KEY constraint failed` |
| DB-NEG-08 | `INSERT INTO shipment_items (shipment_id,item_id,quantity) VALUES (101,999,1)` | `FOREIGN KEY constraint failed` |

DB-NEG-04 and DB-NEG-05 are the evidence behind the role mapping constraint in
[03-角色与账号数据.md](03-角色与账号数据.md) §2.

## 5. State invariants to re-check after every negative case

```sql
-- Row counts must stay at 7 / 3 / 6 / 5 / 6 / 8 for the 101-199 band
SELECT 'users', COUNT(*) FROM users WHERE user_id BETWEEN 101 AND 199
UNION ALL SELECT 'hubs', COUNT(*) FROM hubs WHERE hub_id BETWEEN 101 AND 199
UNION ALL SELECT 'items', COUNT(*) FROM items WHERE item_id BETWEEN 101 AND 199
UNION ALL SELECT 'shipments', COUNT(*) FROM shipments WHERE shipment_id BETWEEN 101 AND 199
UNION ALL SELECT 'shipment_items', COUNT(*) FROM shipment_items WHERE shipment_item_id BETWEEN 101 AND 199
UNION ALL SELECT 'tracking_events', COUNT(*) FROM tracking_events WHERE event_id BETWEEN 101 AND 199;

-- Stock baselines that positive cases depend on
SELECT sku, stock_quantity FROM items WHERE item_id IN (101, 104, 105, 106) ORDER BY item_id;
-- expect IT-WM-101=120 (or 118 after IT-TC-003), IT-LS-104=1, IT-ZS-105=0, IT-UN-106=10

PRAGMA integrity_check;   -- expect "ok"
PRAGMA foreign_key_check; -- expect no rows
```

A negative case that changes any of these values has found a real defect: record
the actual value, the commit SHA and a linked Issue.

## 6. Known non-errors (do not assert as failures)

| Behaviour | Why it is not a failure |
| :--- | :--- |
| `delivered → pending` status change is accepted | Transition order is not enforced (TC-003 note, assumption A-04) |
| A `customer` or `courier` account can create a waybill | `_require_auth()` does not check `role` (assumption A-03) |
| `hub_id: null` on `POST /events` is accepted | The API allows non-hub-local events |
| `current_hub_id` stays `NULL` after `PATCH /status` | Status updates do not move the parcel between hubs |
| `GET /api/shipments` works without a token | The list endpoint is public by design |

Asserting any of the above as an error would produce a false failure against the
current implementation. Raise a change request first if the behaviour must change.
