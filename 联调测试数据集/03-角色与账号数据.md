# 03 · Roles and Accounts · 角色与账号数据

> This file makes the three requested roles concrete and **login-capable**.
> Credentials and hashes are test-only. The machine-readable account rows live in
> [04-联调基础数据.sql](04-联调基础数据.sql) and
> [05-联调基础数据.json](05-联调基础数据.json), both generated by
> `generate_dataset.py`.

## 1. Why seeded accounts cannot be used

`database/schema.sql` inserts `admin_alan`, `customer_alice` and `courier_chan`
with placeholder values `hash_pwd_001` … `hash_pwd_003`. `docs/openapi.yaml`
states explicitly that *"Placeholder seed hashes cannot be used for login"*, and
`verify_password()` in `backend/server.py` rejects any value that is not
`pbkdf2_sha256$600000$<salt>$<digest>`. The only account created with a real
hash is `demo / demo123` (role `admin`, added at first backend startup).

Therefore this dataset creates **seven new accounts with real PBKDF2 hashes** so
each of the three business roles can actually authenticate and drive an
integration case.

## 4. Login contract

```http
POST /api/auth/login
Content-Type: application/json

{"username": "it_merchant_ken", "password": "It@2026Test"}
```

Expected `200`:

```json
{
  "token": "<opaque process-local token>",
  "token_type": "Bearer",
  "user": {"id": 103, "username": "it_merchant_ken", "role": "warehouse_admin"}
}
```

Rules confirmed from `backend/server.py`:

- Both fields must be non-empty strings; the field set must be exactly
  `{username, password}` (400 otherwise).
- An unknown username or bad hash returns 401 `{"error": "invalid credentials"}`.
- Tokens are stored in memory only and **expire on backend restart**; re-login
  after every restart. Tokens are never stored in this dataset.
- `GET /api/auth/profile` with `Authorization: Bearer <token>` returns the same
  `{id, username, role}` object (used by IT-TC-002).

## 5. Permission matrix · 权限矩阵

`_require_auth()` in `backend/server.py` verifies only that the bearer token maps
to an existing `users` row. It **does not compare `role`**. The table below is
therefore an **observed behaviour / gap record**, not a specification to assert.

| Endpoint | Method | Auth required | `customer` | `warehouse_admin` (merchant) | `courier` (driver) | `admin` (`demo`) |
| :--- | :--- | :---: | :---: | :---: | :---: | :---: |
| `/api/health` | GET | No | ✅ | ✅ | ✅ | ✅ |
| `/api/items` | GET | No | ✅ | ✅ | ✅ | ✅ |
| `/api/shipments` | GET | No | ✅ | ✅ | ✅ | ✅ |
| `/api/auth/login` | POST | No | ✅ | ✅ | ✅ | ✅ |
| `/api/auth/profile` | GET | Yes | ✅ | ✅ | ✅ | ✅ |
| `/api/shipments` | POST | Yes | ✅ * | ✅ * | ✅ * | ✅ * |
| `/api/shipments/{id}/status` | PATCH | Yes | ✅ * | ✅ * | ✅ * | ✅ * |
| `/api/shipments/{id}/events` | POST | Yes | ✅ * | ✅ * | ✅ * | ✅ * |

`*` Currently permitted for **every** authenticated role, even though the
business intent assigns creation to the merchant and status/events to the driver.
Integration cases in [06-接口联调用例.md](06-接口联调用例.md) deliberately use the
role-appropriate account for realism, but they must **not** assert that another
role is rejected — that would fail against the current implementation. If
role-based authorisation is required, raise a separate backend task and add new
cases after the API changes.

## 7. Known model gaps · 已知模型缺口

| Gap | Evidence | Effect on integration testing |
| :--- | :--- | :--- |
| No `driver_id` / `courier_id` on `shipments` | `02-数据字典.md` §10 | A driver cannot be assigned to an order through the API; driver involvement is represented only by `tracking_events.hub_id` and `description` text |
| No `merchant` role value | `users.role` CHECK | Merchant is exercised through `warehouse_admin`; do not insert `merchant` |
| No role-based authorisation | `_require_auth()` | Any logged-in role can mutate data; see §5 |
| No delivery signature / photo / ETA fields | `docs/ui/docs/test/test-cases.md` (US-5 blocked) | IT-TC-005 records only status and a textual event, not proof of delivery |
| Dispatch / task assignment not implemented | US-3 blocked in the manual plan | No dispatch dataset is created |
| Status order not enforced | TC-003 note | Do not assert rejection of reverse transitions |

## 8. Account lifecycle and safety

1. Accounts are inserted by `04-联调基础数据.sql` into a disposable database only.
2. They are removed by the same script's `DELETE ... WHERE user_id BETWEEN 101 AND 199`
   block (idempotent reload) or by deleting the disposable `.db` file.
3. Never load this script into `backend/lms.db` on a shared or demo machine.
4. Never reuse `It@2026Test`, the deterministic salts or the fictional phone
   numbers outside this repository's test scope.
5. `demo / demo123` remains the only account created by the application itself;
   keep it for the TC-005 comparison case.
